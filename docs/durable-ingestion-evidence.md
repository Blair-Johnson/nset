# Durable delivery evidence

The durable-ingestion feature was developed in isolated worktrees without changing main or its preview. The server now separates durable intake from query materialization; measurements must distinguish those stages. Operations and retry responsibilities are documented in `docs/durable-ingestion.md`.

## Recovery and regression gates

The integrated Rust/web portion of rx r267 passed 56 Rust tests and all 310 web unit tests. Its Python stage exposed a TensorBoard subprocess import-path fixture error; the corrected invocation in rx r271 passed all 92 then-integrated Python tests, including native HTTP acceptance, SIGKILL/restart replay, capacity retention, concurrent identical-ID replay, authentication, outbox delivery and a real TensorBoard writer-to-native-server recovery journey. These runs preceded the final adapter integration and do not establish W&B or MLflow conformance on their own.

Independent reviews led to fixes for interrupted outbox shutdown, oversized unsendable local batches, malformed journal identity keys, and known-version query databases missing required schema. The outbox follow-up passed 29 focused tests in rx r261 and 100 interrupted-close schedule cases in rx r263. Journal follow-up rx r278 passed 21 focused schema/recovery tests and strict Clippy. TensorBoard follow-up rx r281 passed all 22 tests, including real native-server replay, malformed receipt retention and pending-work query plans. Final combined validation is recorded separately with the compatibility matrix.

## Concurrent delivery probes

rx r283 built the schema-hardened release binary, SHA-256 `db16b05675ade195f356dd2adf26e4a840e85a4a2151399fe181817619195bbe`. rx r285 and r286 are independent workload roots using that same binary, saved query q42. Both use 32 clients/runs, one experiment, 100,000 integer sentinel points, batches up to 1,000, four HTTP workers and two SQLite readers. All observations are first committed to local outboxes. Delivery timers then include retries; query-visibility timers wait for all receipts to become applied. Exact step, timestamp and value readback follows.

With write admission eight, r285 verified all 100,000 points with zero integrity errors and no remaining outbox batches. It observed 1,149 HTTP 503 responses and one transport reset, all retried with stable IDs. Local spooling took 0.814 seconds, server acceptance 1.280 seconds and query visibility 5.223 seconds. The observed acceptance rate was about 78,100 points/second; the query-visible rate was about 19,100.

With write admission sixteen, r286 also verified all 100,000 points with zero integrity errors and no remaining outbox batches. It observed 516 HTTP 503 responses and no transport resets. Local spooling took 0.770 seconds, server acceptance 0.871 seconds and query visibility 1.820 seconds. Observed rates were about 114,800 accepted and 55,000 query-visible points/second.

A larger follow-on, rx r294 (c294/q44), used the same release binary with one million points, 32 clients/runs and eight experiments at admission sixteen. All one million points verified exactly, with zero integrity errors and no remaining outbox batches. It retried 1,091 HTTP 503 responses and one transport reset. Local spooling took 2.234 seconds, durable acceptance 2.301 seconds and query visibility 19.148 seconds. This illustrates the intended buffer between acceptance and projection, not sustained acceptance capacity: once a finite pending queue fills, producers must wait and retry. The same single-trial and development-machine caveats apply.

These are single fresh-database, closed-loop stress trials on a development workstation, with other agent activity not controlled. The deliberately short 20 ms retry interval stresses overload handling; production clients should use backoff and honor Retry-After. The difference between these trials is not a demonstrated scaling factor or a reason to raise defaults universally. Durable data retention through retries is the supported conclusion. No claim is made about sustained capacity, mixed image traffic, bounded total RSS, hardware power-loss behavior or production tail latency.

The first attempt, r280, stopped on a connection reset because the benchmark retried only HTTP 503. The local outbox retained the failed batch; the harness was corrected to retry transport failures with stable IDs and report them separately. Its failure is retained in rx and is not presented as a successful delivery measurement. Temporary benchmark databases are removed on exit; rx retains source snapshots, configuration, binary digests, output and result events.

## Pre-removal integrated verification

rx r305 (independent root, command c302, tags durable/nset/validation) passed the integrated Rust test suite, web unit tests, strict all-target Clippy and formatting in 34.27 seconds. It supersedes r302, which passed tests and Clippy but caught a formatting-only difference in an existing backend test.

MLflow indexed-state follow-up r303 verified bounded identity/latest-value operations and four real SDK journeys. Final input review found that invalid Unicode could poison a pending metadata operation; r306 reproduced that failure, and r307 passed all 18 MLflow tests after validation was moved before durable intent creation. The real-native regression covers invalid parameter/tag/mixed batches, no partial mutation, restart and continued run use.

W&B stream follow-up r304 passed 22 tests, including real SDK init/log/image/finish, restart/resume, outage retry and offline sync twice. Indexed append work no longer scans prior stream rows. Its concurrent HTTP/native test used three clients and stream totals larger than the deliberately small per-request cap, with exact native counts after retries. These are conformance and bounded-work checks, not a production gateway throughput benchmark.

Final W&B review found that an interrupted legacy migration could overwrite a newer pending snapshot. Regression r308 reproduced all six failing cases; r309 fixed and passed the focused cases, and r310 passed all 23 W&B tests with SDKs enabled. The fix drains pending work before file registration/completion and makes the pending legacy snapshot authoritative during migration. The focused fault cases use real SQLite close/reopen with a native receipt test double; the full suite separately exercises the real native service.

Final combined gate rx r311 (independent root, c311, tags compat/nset/sdk/validation) passed all 166 Python tests with no skips in 35.942 seconds (36.80 seconds wall). It enabled the real W&B SDK tests, used the locked compatibility Python environment and the release binary identified above, and promoted ResourceWarning to errors. The suite includes native HTTP/outbox/gateway, MLflow 3.17.2, W&B 0.31.0 and TensorBoard 2.21.0 tests. r311 supersedes r299, whose only failures were gateway fixtures still assuming pre-hash batch IDs and path-prefixed backend URLs. Source snapshot, exact command and retained SDK artifacts are available through `rx show 311`; `rx status -r 305,311` reports both final gates. Browser end-to-end checks and production-scale mixed artifact/load profiling were not rerun for this backend/adapter pass.


## Artifact-removal verification

rx r320 (independent root, c320, tags compat/no-artifacts/regression/sdk) passed all 165 Python tests with no skips in 34.406 seconds (35.32 seconds wall), with ResourceWarning promoted to errors. This integrated both adapters after deleting the shared blob store and signed-file authentication. MLflow artifact APIs and W&B file/media uploads now reject explicitly; official-client scalar/configuration/summary tracking, completion, resume and offline sync remain tested. W&B may emit expected file-upload rejection warnings. Native image logging and TensorBoard event collection are unchanged. No Rust or browser build was needed for this Python-only removal; the earlier artifact and migration results above describe the pre-removal implementation.
